# Авторизация и мультитенантность

Что может видеть соединение, решают три шага.

1. **Тикет** фиксирует пользователя и scope. Он выдаётся по HTTP внутри обычной сессии и
   контекста тенанта.
2. **Scope**: сервер ключует каждый канал scope'ом тикета. Соединение вообще не может
   обратиться к каналам другого scope.
3. **Колбэки каналов** решают, может ли пользователь подписаться на private- и
   presence-каналы.

## Тикеты

`POST /realtime/ticket` по умолчанию использует middleware `web` и `auth`. Ответ:

```json
{"ticket":"9f3c…64 hex chars…","url":"wss://app.example.com/realtime","expires_in":30}
```

- Тикет — 32 случайных байта. Redis хранит его под ключом `sha256(ticket)` с TTL
  `ticket.ttl` (по умолчанию 30 с).
- Сервер погашает его через `GETDEL` во время WebSocket upgrade, поэтому каждый тикет
  открывает ровно одно соединение.
- Тикет несёт auth-идентификатор пользователя, guard (`realtime.ticket.guard` или `null`
  для guard по умолчанию) и scope.
- Scope берётся из `Realtime::resolveScopeUsing()`, вычисляемого во время запроса тикета.

Маршрут можно изменить через `realtime.routes` (префикс и middleware) или отключить и
выдавать тикеты самостоятельно:

```php
Route::middleware(['api', 'auth:sanctum'])->post('/api/realtime/ticket', function (Request $request) {
    return Realtime::issueTicket($request->user(), 'sanctum', scope: tenant()->id, request: $request);
});
```

## Scope

```php
Realtime::resolveScopeUsing(fn (): string => (string) app(CurrentTenant::class)->id());
```

Резолвер используется дважды:

- при выдаче тикета — чтобы зафиксировать scope соединения;
- при публикации (`Realtime::publish()`, broadcasting) без явного scope.

Значит, очередная задача `ShouldBroadcast` должна выполняться в контексте тенанта — для
мультитенантных очередей это и так необходимо. Scope можно и закрепить:

- для вызова: `Realtime::publish($channel, $event, $data, scope: 'acme')`;
- для broadcasting-подключения: `['driver' => 'realtime', 'scope' => 'central']`.

Scope может содержать `[A-Za-z0-9_\-.:]` и не длиннее 100 байт. Пустая строка — допустимый
scope и значение по умолчанию для однотенантных приложений.

## Колбэки каналов

```php
use Dskripchenko\Realtime\Facades\Realtime;

// private-board.{id}
Realtime::channel('board.{id}', function (User $user, string $id): bool {
    return $user->boards()->whereKey($id)->exists();
});

// presence-page.{id}: return the member info shown to others
Realtime::channel('page.{id}', function (User $user, string $id): array|false {
    return $user->can('view', Page::find($id)) ? ['name' => $user->name, 'avatar' => $user->avatar_url] : false;
});
```

Как колбэки сопоставляются и вызываются:

- Шаблон сопоставляется с именем канала без префикса `private-` или `presence-`.
  Плейсхолдеры `{name}` соответствуют одному сегменту между точками и передаются по
  порядку как строки. Неявная привязка моделей недоступна.
- Для private-каналов подписку разрешает любое истинное значение.
- Для presence-каналов возвращённый массив становится `info` участника. `true` означает
  пустой `info`.
- Private- или presence-канал без подходящего колбэка **запрещён**.
- Публичным каналам колбэк не нужен.
- Если колбэк бросает исключение, подписка отклоняется с `forbidden`, а исключение уходит
  в ваш обработчик исключений.

### Колбэки выполняются в realtime-сервере

Колбэки выполняются внутри процесса `realtime:serve`, а не в HTTP-запросе. Сервер
вызывает их напрямую, без дополнительного HTTP-запроса. Поэтому:

- `request()`, сессия, cookie и `auth()->user()` недоступны или ни к чему не относятся.
  Используйте аргумент `$user`.
- Пользователь загружается один раз на подписку через user provider guard'а
  (`retrieveById`). Загружать пользователей иначе можно так:

  ```php
  Realtime::resolveUserUsing(fn (Ticket $ticket) => User::query()->find($ticket->userId));
  ```

- Колбэки каналов регистрируются в сервис-провайдерах, поэтому серверный процесс должен
  загружать те же провайдеры, что и веб-приложение. Как artisan-команда он так и делает.

### Вход в тенант (`authorizeUsing`)

В мультитенантном приложении (например, схема на тенанта) загрузка пользователя и колбэки
должны выполняться внутри тенанта тикета. Оберните их:

```php
use Dskripchenko\Realtime\Auth\Ticket;

Realtime::authorizeUsing(function (Ticket $ticket, Closure $next): mixed {
    return Tenancy::run($ticket->scope, $next);   // enter, call $next(), always leave
});
```

Хук:

- получает `Ticket` (`userId`, `guard`, `scope`, `issuedAt`);
- должен вернуть то, что возвращает `$next()`, либо `false`, чтобы отказать, не вызывая
  его (например, когда тенанта тикета больше нет или он приостановлен);
- выполняется один раз на подписку;
- должен восстанавливать предыдущий контекст даже при исключениях (`try`/`finally`),
  потому что процесс обслуживает все тенанты.

## Чек-лист усиления защиты

- Предпочитайте private-каналы. Публичные каналы видны любому вошедшему пользователю того
  же scope.
- Держите `ticket.ttl` коротким. Тикеты передаются в строке запроса, поэтому убедитесь,
  что прокси не пишет query string в лог для realtime-location, либо примите, что
  одноразовые тикеты в логах безвредны после использования или истечения.
- Задайте `allowed_origins`.
- Делайте presence-`info` минимальным: его видит каждый участник канала.
- Клиентские события (`client-*`) приходят напрямую от других пользователей. Считайте их
  `data` недоверенным вводом и отключите их через `client_events => false`, если они не
  нужны.
- Отзыв доступа не разрывает существующие подписки: авторизация проверяется при подписке.
  Чтобы немедленно отключить пользователя, опубликуйте событие, по которому клиент
  отпишется, или перезапустите сервер. Принудительного отключения отдельного соединения в
  0.1 нет.
