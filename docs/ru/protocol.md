# Протокол

Каждое сообщение — JSON-объект, отправленный как **текстовое** сообщение WebSocket.
Бинарное сообщение закрывает соединение с кодом 1003. У каждого сообщения есть поле
`type`.

Сообщение клиента может нести `id` — целое число или строку до 64 символов. Сервер
копирует `id` в ответ `ack`, `error`, `pong` или `presence`, чтобы клиент мог сопоставить
ответы с запросами.

## Подключение

```text
GET /?ticket=<ticket> HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Version: 13
Sec-WebSocket-Key: ...
Origin: https://app.example.com
```

Сервер может отклонить upgrade с одним из HTTP-статусов:

| Статус | Причина |
|--------|--------|
| 400 | Некорректный запрос upgrade |
| 401 | Тикет отсутствует, неизвестен, истёк или уже использован |
| 403 | `Origin` не входит в `realtime.allowed_origins` |
| 426 | `Sec-WebSocket-Version` не равен 13 |
| 431 | Заголовок запроса больше 8 КиБ |
| 503 | Достигнут лимит соединений или хранилище тикетов недоступно |

Браузер не видит эти статусы: API `WebSocket` сообщает только код закрытия 1006.
Клиентам следует получать новый тикет перед каждой попыткой — так и делает JS-клиент.

При успешном upgrade сервер отправляет приветствие:

```json
{"type":"welcome","socket_id":"4161587040080015970.4500350542000801717","heartbeat":25}
```

- `socket_id` — значение для заголовка `X-Socket-ID` в HTTP-запросах, чтобы
  `broadcast(...)->toOthers()` пропускал это соединение.
- `heartbeat` — интервал keepalive сервера в секундах.

## Каналы

| Имя | Тип | Кто может подписаться |
|------|------|-------------------|
| `news`, `board.42.public` | public | любое соединение того же scope |
| `private-board.42` | private | колбэк для `board.{id}` вернул истинное значение |
| `presence-page.7` | presence | колбэк для `page.{id}` вернул истинное значение; возвращённый массив становится `info` участника |

Имя канала соответствует `[A-Za-z0-9_\-=@,.;:]+` и не длиннее 200 байт. Внутри сервера и в
Redis каждый канал хранится под ключом `<scope>/<name>`, где scope берётся из тикета. Два
тенанта, подписанные на `private-board.1`, используют два разных канала.

## Клиент → сервер

### subscribe

```json
{"type":"subscribe","id":1,"channel":"private-board.42"}
{"type":"subscribe","id":2,"channel":"private-board.42","since":17}
```

`since` — последний номер, который клиент применил. При первой подписке его не передают.

Сервер отвечает `ack`. Для presence-каналов в `ack` есть ещё список `members`:

```json
{"type":"ack","id":2,"channel":"private-board.42","seq":19,"gap":false}
{"type":"ack","id":3,"channel":"presence-page.7","seq":0,"gap":false,
 "members":[{"id":7,"info":{"name":"Ann"}}]}
```

После `ack` сервер отправляет события с `since + 1` до текущей головы, от старых к новым.
Затем идут живые события. Поля `ack`:

- `seq` — текущая голова канала.
- `gap: true` означает, что пропущенные события уже нельзя проиграть: пропущено больше
  `realtime.replay.size` событий, журнал истёк или канал был сброшен (`since` > головы).
  В этом случае ничего не проигрывается. Клиент должен перезагрузить состояние (например,
  по HTTP) и продолжить с `seq`.

Повторная подписка на канал, который у соединения уже есть, возвращает ещё один `ack` и
ничего не меняет.

Ошибки приходят с `code` `forbidden` (колбэк отказал или для private/presence-канала нет
колбэка), `bad_channel`, `limit` (больше `limits.max_subscriptions`) или `unavailable`
(Redis недоступен):

```json
{"type":"error","id":1,"channel":"private-board.13","code":"forbidden","message":"Subscription denied: forbidden"}
```

### unsubscribe

```json
{"type":"unsubscribe","id":4,"channel":"private-board.42"}
```

Ответ — `{"type":"ack","id":4,"channel":"private-board.42"}`. В presence-канале остальные
участники получают `leave`, если это было последнее соединение пользователя.

### presence (list)

```json
{"type":"presence","id":5,"channel":"presence-page.7","action":"list"}
```

Ответ — `{"type":"presence","id":5,"channel":"presence-page.7","action":"list","members":[...]}`.
Клиенты не могут отправлять `join` или `leave`: они следуют из подписки.

### event (клиентские события)

```json
{"type":"event","id":6,"channel":"presence-page.7","event":"client-typing","data":{"on":true}}
```

Клиентские события доставляются остальным подписчикам канала на всех серверах. Они нужны
для индикаторов набора текста, курсоров и подобных кратковременных сигналов. Правила:

- Соединение уже должно быть подписано на канал.
- Канал должен быть private или presence.
- Имя события должно соответствовать `client-<name>`.
- `realtime.client_events` должен быть включён.

У клиентских событий нет номера, и они не проигрываются повторно. Если передан `id`,
отправитель получает `ack`. Получатели видят id пользователя-отправителя:

```json
{"seq":null,"type":"event","channel":"presence-page.7","event":"client-typing","data":{"on":true},"user_id":2,"except":"..."}
```

### ping

```json
{"type":"ping","id":"p1"}
```

Ответ — `{"type":"pong","id":"p1"}`. Браузеры не умеют отправлять ping-фреймы WebSocket,
поэтому этим сообщением клиент проверяет, что связь жива. Сервер и сам отправляет
ping-фреймы (см. «Keepalive» ниже).

## Сервер → клиент

### event

```json
{"seq":21,"type":"event","channel":"private-board.42","event":"CardMoved","data":{"card":5}}
```

- `seq` растёт на единицу с каждым опубликованным в канале событием. Клиенты должны
  игнорировать событие с `seq` ≤ последнего применённого, потому что replay и живая
  доставка на мгновение могут пересекаться.
- `seq: null` помечает сообщения, которые не проигрываются: presence-уведомления и
  клиентские события.
- `except` — внутреннее поле: id сокета, который сервер пропустил.

### presence-уведомления

```json
{"seq":null,"type":"presence","channel":"presence-page.7","action":"join","member":{"id":2,"info":{"name":"Bob"}}}
{"seq":null,"type":"presence","channel":"presence-page.7","action":"leave","member":{"id":2,"info":{"name":"Bob"}}}
```

`join` отправляется, когда у пользователя появляется первое соединение с каналом.
`leave` — когда уходит последнее. Несколько вкладок одного пользователя — один участник.
Подключающееся соединение тоже получает свой `join`.

### resync

```json
{"type":"resync","channel":"private-board.42","seq":250}
```

Сервер отправляет `resync`, когда его собственный канал pub/sub к Redis был недоступен
дольше, чем покрывает буфер replay. Клиенту следует перезагрузить состояние и продолжить
с `seq`.

### error

```json
{"type":"error","id":7,"code":"bad_request","message":"Field \"channel\" is required"}
```

| Код | Значение |
|------|---------|
| `bad_request` | Некорректный JSON или поля |
| `unknown_type` | Неподдерживаемый `type` |
| `bad_channel` | Некорректное имя канала |
| `forbidden` | В авторизации отказано или клиентское событие запрещено |
| `not_subscribed` | `presence`/`event` для канала, на который соединение не подписано |
| `limit` | Слишком много подписок |
| `unavailable` | Redis временно недоступен |
| `internal` | Непредвиденная ошибка сервера (пишется в лог) |

Ошибки никогда не закрывают соединение.

## Keepalive

- Сервер отправляет ping-фрейм после `heartbeat.interval` секунд тишины (по умолчанию
  25). Он закрывает соединение с кодом 4000, если за `heartbeat.timeout` секунд (по
  умолчанию 20) ничего не пришло.
- Клиенты отправляют `{"type":"ping"}` после одного интервала heartbeat тишины. После
  двух интервалов они разрывают связь и переподключаются.

## Коды закрытия

| Код | Когда |
|------|------|
| 1000 | Обычное закрытие (сервер возвращает код клиента) |
| 1001 | Сервер останавливается |
| 1002 | Ошибка протокола (немаскированный фрейм, неверный opcode, биты RSV, неверное продолжение, неверная полезная нагрузка close) |
| 1003 | Бинарное сообщение |
| 1007 | Текстовое сообщение — не корректный UTF-8 |
| 1008 | Превышен лимит частоты (`limits.messages_per_second`) |
| 1009 | Фрейм или сообщение больше лимитов |
| 4000 | Тайм-аут keepalive |
| 4008 | Медленный потребитель: ждут отправки больше `limits.max_buffer` байт |

## Не поддерживается

- Расширения, включая permessage-deflate. Биты RSV должны быть нулевыми.
- Подпротоколы. `Sec-WebSocket-Protocol` игнорируется.
