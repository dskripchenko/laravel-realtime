# Сервер

```bash
php artisan realtime:serve [--host=0.0.0.0] [--port=6001] [--server-id=rt-1] [-v]
```

Сервер — это artisan-команда, поэтому приложение полностью загружено. Сервер загружает
ваши сервис-провайдеры и выполняет ваши колбэки каналов, а провайдеры пользователей и
подключения к базе данных берутся из того же контейнера.

При старте он печатает одну строку: `Realtime server listening on <host>:<port> (id <id>)`.
С `--port=0` свободный порт выбирает ОС. Флаг `-v` включает и информационные строки лога.

## Как это работает

Сервер — однопоточный цикл вокруг `stream_select()`. Цикл следит за:

- слушающим сокетом;
- каждым клиентским сокетом (на чтение, а пока есть неотправленные данные — и на запись);
- одним «сырым» RESP-соединением с Redis, по которому приходят сообщения pub/sub.

`subscribe()` в phpredis блокирует процесс, поэтому не может делить цикл с клиентскими
сокетами. Поэтому канал pub/sub обслуживает небольшой встроенный RESP-клиент. Все
остальные обращения к Redis (публикация, replay, тикеты, presence) идут через ваше
phpredis-подключение Laravel. Каждое из них — один round trip.

Что делает одна итерация:

1. Принимает новые соединения, не больше 100 за итерацию.
2. Читает из готовых сокетов:
   - Во время рукопожатия собирает HTTP-заголовок (не больше 8 КиБ). Проверяет upgrade,
     погашает тикет, отправляет `101`, а затем `welcome`.
   - Когда соединение открыто, инкрементально декодирует фреймы, собирает
     фрагментированные сообщения, отвечает на ping и запускает обработчик протокола.
3. Читает сообщения pub/sub и доставляет каждое локальным подписчикам. Фрейм кодируется
   один раз на сообщение, а не на каждое соединение.
4. Пишет накопленный вывод без блокировки. При частичной записи остаток буфера
   сохраняется.
5. Раз в секунду запускает таймеры: тайм-ауты рукопожатия, keepalive-пинги, тайм-ауты
   закрытия, heartbeat сервера в Redis (каждые 10 с), уборку мёртвых серверов (каждые
   15 с) и проверку канала pub/sub.

Бэкенд на ext-event в 0.1 **не реализован**. `stream_select()` ограничен `FD_SETSIZE` —
в сборках PHP это обычно 1024 дескриптора на процесс. Для большего числа соединений
запускайте несколько процессов (см. [эксплуатацию](operations.md)).

## Гарантии порядка и доставки

- События одного канала доходят до каждого подписчика в порядке номеров. Номер
  присваивается в Redis одним Lua-скриптом, который заодно дописывает событие в журнал
  replay и публикует его.
- Доставка — не более одного раза на соединение. Клиент, переподключившийся с `since`,
  получает пропущенные события, если они ещё в буфере replay. Иначе он получает
  `gap: true` и должен перезагрузить своё состояние.
- Подписываясь на канал впервые, сервер ждёт подтверждения подписки от Redis и только
  потом читает журнал replay. Ничего опубликованного в промежутке не теряется, а
  доставленное дважды отбрасывается по номеру.
- Если канал pub/sub сервера к Redis рвётся, сервер переподключается с нарастающей
  задержкой (0,5 с, затем удвоение до 30 с). Затем он проигрывает каждый свой канал с
  последнего увиденного номера. Каналы, выпавшие из буфера, получают сообщение `resync`.

## Конфигурация

`config/realtime.php` (публикуется командой `php artisan vendor:publish --tag=realtime-config`):

| Ключ | По умолчанию | Значение |
|-----|---------|---------|
| `server.host` / `server.port` | `0.0.0.0` / `6001` | Адрес привязки |
| `server.reuse_port` | `false` | `SO_REUSEPORT`: несколько процессов на одном порту (Linux) |
| `public_url` | `null` | URL, возвращаемый вместе с тикетом, например `wss://app.example.com/realtime` |
| `allowed_origins` | `[]` | Список разрешённых Origin (`https://a.example.com`, `*.example.com`); пустой разрешает любой |
| `redis.connection` | `default` | phpredis-подключение из `database.redis` |
| `redis.prefix` | `realtime:` | Префикс всех ключей и каналов pub/sub |
| `ticket.ttl` | `30` | Время жизни тикета, секунды |
| `ticket.guard` | `null` | Guard для тикетов и загрузки пользователя (`null` = guard по умолчанию) |
| `routes.*` | включён, `realtime`, `['web','auth']` | Маршрут тикетов `POST /realtime/ticket` |
| `scope` | `''` | Scope по умолчанию, если резолвер не зарегистрирован |
| `replay.size` | `100` | Сколько событий на канал хранится для replay |
| `replay.retention` | `86400` | Сколько секунд неактивный канал хранит счётчик и журнал |
| `heartbeat.interval` / `heartbeat.timeout` | `25` / `20` | Keepalive, секунды |
| `limits.max_connections` | `1000` | На процесс; лишние соединения получают HTTP 503 (см. замечание о `FD_SETSIZE` выше) |
| `limits.max_frame_size` / `limits.max_message_size` | `65536` | Байты; больше — закрытие с кодом 1009 |
| `limits.max_subscriptions` | `100` | Каналов на соединение |
| `limits.max_buffer` | `4194304` | Байт неотправленного вывода на соединение до закрытия с кодом 4008 |
| `limits.messages_per_second` | `50` | Token bucket на соединение; превышение закрывает с кодом 1008 |
| `limits.handshake_timeout` | `10` | Секунд на завершение HTTP upgrade |
| `client_events` | `true` | Разрешить события `client-*` в private- и presence-каналах |

Замечания о подключении к Redis:

- Собственная опция `prefix` подключения и сериализатор **не** используются. Каждая
  команда идёт через `rawCommand()`, поэтому веб-процессы и серверы одинаково понимают
  имена ключей, какими бы ни были опции подключения.
- Сокет pub/sub берёт `host`, `port`, `username`, `password`, `scheme` (`tls`) и `url` из
  той же конфигурации подключения.
- Redis Cluster и predis не поддерживаются.

## Health

`GET /health` на порту сервера возвращает JSON:

```json
{"status":"ok","server_id":"rt-1","connections":12,"channels":5,"redis":true,"uptime":3600,"memory":31457280}
```

Статус — 200, либо 503 с `"status":"degraded"`, пока канал pub/sub к Redis недоступен.
Любой другой запрос, не являющийся upgrade, получает 404.

## Остановка

По SIGTERM или SIGINT (нужен ext-pcntl) сервер:

1. отправляет каждому клиенту код закрытия 1001;
2. удаляет presence-записи клиентов;
3. до одной секунды досылает вывод;
4. снимает свою регистрацию в Redis и завершается.

Клиенты переподключаются к другому экземпляру и проигрывают события с последнего номера.

## Особенности долгоживущего процесса

- Колбэки каналов и провайдеры пользователей работают в одном процессе всё время его
  жизни. Избегайте статических кэшей, растущих без ограничений, и не храните состояние
  запроса.
- Соединение с базой данных может «протухнуть» между подписками. Laravel
  переподключается при ошибках «lost connection». Если ваша база агрессивно закрывает
  простаивающие соединения, вызывайте `DB::reconnect()` в хуке `authorizeUsing()` или
  периодически перезапускайте сервер (перезапуски берёт на себя supervisor).
- Деплой: перезапускайте сервер после каждого деплоя, чтобы он загрузил новый код, — так
  же, как воркеры очередей.
